# HyperFrames Review Player Integration - Implementation Note

Status: implementation candidate complete; pilot cutover deferred until existing browser drafts are exported or explicitly retired
Last updated: 2026-07-24
Related proposal: [hyperframes-review-integration.md](hyperframes-review-integration.md)

## Purpose

Maintain the implementation state for adding an optional HyperFrames Review Player to FrameCue. Update this note whenever implementation decisions, user feedback, validation results, or scope change.

The integration keeps the responsibility boundary from the proposal:

- HyperFrames is the only source of playable visuals and the full narration timeline.
- FrameCue is the only source of cue/block edits, review decisions, drafts, and exports.
- FrameCue remains a review gate. This work does not render or publish video.

## Current Baseline

### FrameCue repository

- `viewer.html` supports Cue and Block review plus an optional Still/Video stage.
- `framecue_manifest.json` can switch multiple packages in one page and may declare a same-origin `review_player` per item.
- Drafts and export filenames are isolated by manifest item ID.
- `framecue.py` builds a single review package and copies `viewer.html`; it does not create a multi-package manifest.
- The pilot package uses a custom schema and asset layout. It was not generated by the current `framecue.py`, which requires a video and emits different scene names and metadata.
- The viewer validates Player source and origin, keeps playback highlighting separate from editor selection, and arbitrates Player, cue-audio, and optional redraw-video playback.
- There is no automated browser test suite in the repository.

## Baseline Audit Findings

### Ready to reuse

- FrameCue manifest item IDs already provide the correct isolation boundary.
- Cue, scene, and composition timings align closely enough for the pilot.
- The current player already provides a stable audio-clock-to-composition loop.
- Both applications are framework-free HTML/CSS/JavaScript and can be integrated without a new dependency.
- The pilot can be served from one origin by serving the project root.

### Targets implemented in the candidate

- A generic Review Player configuration format.
- An optional Still/Video stage control and portrait player surface in FrameCue.
- A stable `postMessage` contract and origin/source validation.
- Cue selection to player seek, plus player time to cue highlighting.
- Audio arbitration across Review Player narration, composition narration, per-cue audio, and redraw `fullVideo`.
- Ready timeout and non-blocking failure state.
- Browser validation for old packages, player packages, and multi-package switching.

### Merge path used

The pilot's `review/framecue/index.html` is not identical to the open-source `FrameCue/viewer.html`. It contains global redraw-review additions. The implementation therefore did not overwrite either variant.

The implementation used this merge path:

1. Implement the Video stage mode and protocol in the open-source `FrameCue/viewer.html`.
2. Port the same small integration into the global FrameCue viewer while preserving redraw features.
3. Create a separate pilot candidate and defer replacement of the existing page until its browser/exported review state is preserved.

### Claude Fable and Grok 4.5 review

Both reviewers independently returned `REVISE`, with the same conclusion: the architecture is suitable, but the specification needed small corrections before P1.

Accepted findings:

- Fix the pilot player path in the proposal and resolve player/config asset paths from the document that declares them.
- Define positive readiness conditions and a non-blocking `hyperframes:error` path instead of treating iframe `load` as ready.
- Use numeric playback time as the only cross-component synchronization key for the MVP.
- Give player-originated updates a highlight-only path that does not call the current `go()` navigation function.
- Explicitly arbitrate every audible element, including the composition narration and the redraw viewer's `fullVideo`.
- Preserve/export drafts before any origin, port, pathname, or manifest item ID migration.
- Keep Cue and Block review visible while Video replaces only the stage, and size the player from its portrait dimensions.
- Treat the pilot package as a custom artifact; do not rebuild it with the current `framecue.py`.

Qualified or deferred findings:

- Keep `scenes` in `review-player.json` because the standalone Player needs its own scene menu. That file is authoritative for Player scene labels/times; FrameCue remains authoritative for review scenes. Scene IDs do not cross the message boundary.
- Defer `hyperframes:scenechange`. Cue synchronization by time covers the MVP without defining a brittle scene-ID mapping.
- No recommendation required changing the framework-free architecture or reversing the open-source-first, redraw-port-second merge order.

Rejected findings: none after source verification. The two scope-sensitive suggestions were qualified above rather than copied literally.

## Proposed MVP Design

### Review Player configuration

Keep project-specific playback data beside each HyperFrames project in `review-player.json`:

```json
{
  "composition": "index.html",
  "audio": "assets/audio/yuanyuan-perseus.wav",
  "width": 1080,
  "height": 1920,
  "scenes": [
    { "id": "scene-01", "label": "01 一個月後", "start": 0.04 }
  ]
}
```

The generic player may default to `review-player.json` and accept a `?config=` override. Resolve `composition` and `audio` relative to the loaded config URL, not the FrameCue page or Player script URL. Derive duration from the narration audio's `loadedmetadata`; do not maintain a duplicate duration or cosmetic status value in config.

The Player config is authoritative for its standalone dimensions and scene menu. The review package remains authoritative for FrameCue scenes. FrameCue only receives time and duration from the Player and must not read or duplicate the Player config.

### FrameCue manifest

For the pilot, serve the project root and add this optional field to the FrameCue item:

```json
{
  "items": [
    {
      "id": "yuanyuan-computex-2026",
      "label": "Yuanyuan COMPUTEX 2026",
      "review_package": "review_package.json",
      "semantic_blocks": "semantic_blocks/semantic_blocks.json",
      "review_player": {
        "type": "hyperframes",
        "src": "../../hyperframes/player.html"
      }
    }
  ]
}
```

`review_player.src` resolves relative to the FrameCue page. The pilot must be served from the project root so `/review/framecue/` can load `/hyperframes/` on the same origin.

### Message contract

Use plain objects with numeric seconds:

| Direction | Payload |
|---|---|
| FrameCue -> Player | `{ "type": "framecue:seek", "time": 12.34 }` |
| FrameCue -> Player | `{ "type": "framecue:play", "time": 12.34 }` (`time` optional) |
| FrameCue -> Player | `{ "type": "framecue:pause" }` |
| Player -> FrameCue | `{ "type": "hyperframes:ready", "duration": 81.09, "width": 1080, "height": 1920 }` |
| Player -> FrameCue | `{ "type": "hyperframes:timeupdate", "time": 12.34, "playing": true }` |
| Player -> FrameCue | `{ "type": "hyperframes:error", "code": "composition_unavailable", "message": "..." }` |

The Player sends `hyperframes:ready` only after all of these are true:

- `review-player.json` loaded and validated;
- the inner composition iframe fired `load`;
- the same-origin composition exposes a callable `contentWindow.__hf.seek`;
- the full narration audio has readable metadata and a finite duration;
- every composition `audio` and `video` element has been paused and muted.

Config, composition, timeline API, or audio failures send `hyperframes:error`. FrameCue shows a non-blocking unavailable state and leaves Cue and Block review usable.

The MVP is same-origin. FrameCue must verify both `event.source === playerIframe.contentWindow` and `event.origin === location.origin`. The Player must verify both `event.source === window.parent` and `event.origin === location.origin`. Both sides use `location.origin` as `postMessage`'s `targetOrigin`; neither side uses `*`.

Send playback time at about 20 Hz while playing. This keeps cue highlighting within the 100 ms target without sending every animation frame across the iframe boundary.

### Synchronization rules

- A user-selected cue sends one seek to the Player.
- A player-originated time update changes a separate playback highlight without sending a seek back.
- During a gap between cues, keep the most recent cue highlighted.
- The highlight-only path may toggle stable CSS classes and perform nearest-item scrolling. It must not call `go()`, change the selected editor cue, replace editor or prompt values, change the per-cue audio source, rebuild Cue/Risk/Block lists, synchronize the block editor, save drafts, or alter exports/approval state.
- Package switching unloads the old player and resets ready/time state.

### Audio ownership

- The Review Player owns full narration playback.
- The composition's `#narration` remains present for HyperFrames inspection but is paused and muted before the Player reports ready.
- Entering Video pauses FrameCue's per-cue audio and the redraw viewer's `fullVideo`.
- Leaving Video pauses the Review Player.
- Playing a per-cue clip pauses the Review Player and `fullVideo` first.
- Playing `fullVideo` pauses the Review Player and per-cue audio first.
- In Cue scope, the global Space shortcut routes to the active playback context: Review Player in Video stage mode, per-cue audio in Still stage mode, and never both. In semantic-block scope, Space pauses playback, approves a valid block, and selects the next block.
- At no time may more than one of the Review Player narration, composition narration, per-cue audio, or redraw `fullVideo` be audible.

### UI behavior

- Show a Still/Video stage control only when the current item has a valid `review_player` object. Do not add Video as a third mutually exclusive Cue/Block review pane.
- Video replaces the static stage with the embedded Review Player while the current Cue or Block pane remains visible.
- Keep Still as the default stage mode for compatibility; do not force Video open.
- Size the embedded surface from the Player config's width/height so the 1080x1920 pilot remains portrait and fits without clipped controls.
- Show a loading state until `hyperframes:ready`.
- On `hyperframes:error` or readiness timeout, show Player unavailable while leaving Cue and Block fully usable.
- Old packages without `review_player` must render exactly as before.

## Risks and Constraints

- Serving only `review/framecue/` cannot reach the sibling `hyperframes/` directory. The pilot integration must serve the project root or build a self-contained review bundle.
- Player config asset paths resolve relative to the config URL. FrameCue manifest paths resolve relative to the FrameCue page. Mixing those bases will produce silent 404s.
- Native `<audio>` `timeupdate` is too sparse for the 100 ms synchronization target; use a throttled animation-frame loop.
- Calling the normal cue navigation function from player updates creates more than a seek feedback loop: it also resets editor values, cue audio, and lists. Player tracking needs a separate highlight-only path.
- Browser autoplay rules still require a user gesture before full narration can start.
- Review Player narration must be served by an HTTP server with byte-range support. Python 3.9's basic `http.server` returned HTTP 200 without `Accept-Ranges` and could not seek the WAV reliably; the validated miniserve setup returned HTTP 206.
- A failed iframe can still emit a browser `load` event. Treat the complete Player readiness predicate, not iframe load, as readiness, and surface a typed error on failure.
- Review package browser drafts live in localStorage and are keyed by origin, pathname, and manifest item ID. Preserve/export review state before changing any of those values or replacing a package viewer.
- The pilot review package is custom and cannot be regenerated by the current `framecue.py` without changing its schema and assets.
- HyperFrames 0.6.55 was used by the pilot; do not mix a version upgrade into this integration.

## External Components Evaluated

The viewer refactor should not replace FrameCue with a full subtitle editor or
video editor. FrameCue needs a portable, package-local review surface with Cue,
Block, redraw, and optional HyperFrames playback. No evaluated full application
matches that boundary without adding a server, a framework runtime, or an
unrelated editing model.

| Component | Adopt only when | Decision |
|---|---|---|
| [wavesurfer.js](https://github.com/katspaugh/wavesurfer.js) with its [Regions plugin](https://wavesurfer-js.pages.dev/docs/classes/plugins_regions.RegionsPlugin) | Reviewers must directly inspect or drag Cue start/end timing against a waveform | Best future addition. Keep the native cue-audio control until that requirement is accepted. For long audio, generate pre-decoded peaks; do not depend on a CDN. |
| [Video.js](https://github.com/videojs/video.js) | FrameCue must play ordinary MP4/HLS/DASH media with standard text tracks across browsers | Defer. Native media elements remain smaller for current package assets, and Video.js does not replace the HyperFrames iframe protocol. |
| [webvtt.js](https://github.com/annevk/webvtt) | FrameCue needs spec-compliant WebVTT import, parsing, or serialization | Defer. It is a parser/validator, not a review UI; current SRT packaging does not need it. |

Keep [Subtitle Edit](https://github.com/SubtitleEdit/subtitleedit) as an
external specialist tool for exceptional timing repair, not an embeddable
dependency. Do not adopt server-backed review apps such as
[OpenVidReview](https://github.com/davidguva/OpenVidReview), or React/Remotion
video-editor foundations such as
[React Video Editor](https://github.com/reactvideoeditor/free-react-video-editor),
for the canonical viewer. They solve a different product problem and would make
review packages less portable.

The default refactor path is therefore: one canonical FrameCue viewer, native
browser media controls, and no new dependency. Revisit only when a concrete
timing-edit, standards-playback, or WebVTT-import requirement is accepted.
